31 · Software Engineering & Testing

Module J · Software engineeringAsked in 2023 and 2025 Process models, testing, metrics, maturity levels and risk.

Start here

Software engineering is the discipline of building software in an organised, measurable, repeatable way, as opposed to ad-hoc coding. It covers the life of a project: requirements → design → coding → testing → maintenance. This is the software development life cycle (SDLC).

  • Waterfall: finish each phase before starting the next. Simple but rigid.
  • Incremental / iterative: build and deliver in pieces.
  • Spiral: repeated cycles with explicit risk analysis.
  • Prototype: build a quick model to clarify requirements.
  • Agile: short iterations, close customer feedback.

Testing

Testing is running the software to find defects. Levels of testing, from smallest to largest:

LevelWhat is tested
UnitIndividual functions/modules, by the developer
IntegrationHow modules work together (their interfaces)
SystemThe complete system against the specification
AcceptanceDoes it satisfy the customer's needs? Alpha testing is done at the developer's site by internal users; beta testing is done at the customer's site by real users. Both are forms of acceptance testing.

The V-model

The V-model pairs each development phase with the test that checks it:

Black-box vs white-box

Black-boxWhite-box (glass-box)
Based onSpecification only; ignore internalsThe code's internal structure
TechniquesEquivalence partitioning, boundary value analysisStatement coverage, branch coverage, condition coverage, MC/DC, path coverage, cyclomatic complexity

Grey-box testing uses partial knowledge of the internals.

  • MC/DC = Modified Condition/Decision Coverage: each condition inside a decision must be shown to independently affect the decision's outcome. Required for safety-critical software (aerospace).
  • Regression testing: re-running earlier tests after a change to the software to make sure nothing that used to work is now broken.

Cyclomatic complexity

Draw the program's control-flow graph (nodes = blocks of code, edges = possible jumps). McCabe's cyclomatic complexity measures the number of independent paths, hence the minimum number of tests needed for full path coverage. It belongs to white-box testing.

V(G) = E − N + 2P, with E edges, N nodes and P connected components (P = 1 for one program, giving E − N + 2). Equivalent shortcuts: V(G) = (number of decision points, like if/while) + 1, or the number of regions of the flow graph.

Worked example

A function with one if and one while has 2 decisions, so V(G) = 2 + 1 = 3 independent paths. Equivalently, a flow graph with 7 edges and 6 nodes gives 7 − 6 + 2 = 3.

Process maturity: CMM

The Capability Maturity Model rates how mature an organisation's software process is on five levels:

1 Initial → 2 Repeatable → 3 Defined → 4 Managed → 5 Optimizing

Mnemonic: I R D M O. (Initial = chaotic, ad hoc; Repeatable = basic project management; Defined = standard processes documented across the organisation; Managed = measured quantitatively; Optimizing = continuous improvement.)

Risk management

A risk is something that might go wrong. The stages, in order: risk identification → risk analysis → risk planning → risk monitoring. (First you must find the risks, then judge how likely and how damaging they are, then plan what to do, then watch them.)

Design metrics

  • Fan-in of a function X = the number of functions that call X. Fan-out = the number of functions that X calls.
  • High fan-in means X is heavily used and tightly coupled to the rest of the design (changing it affects many callers). High fan-out means X depends on many others, so its own complexity is probably high.
  • Coupling = how much modules depend on each other (aim for low). Cohesion = how closely a module's parts belong together (aim for high).

Estimation: function points

Function points (FP) measure the size of software from its functionality, independent of programming language. Count five things and weight them:

UFP (unadjusted function points) = Σ (count × weight) over: user inputs, user outputs, user enquiries, internal files, external interfaces.
CAF (complexity adjustment factor) = 0.65 + 0.01 × Σ Fᵢ, over 14 factors, each rated 0–5.
FP = UFP × CAF

Worked example (2025 question)

Inputs 30 × 4 = 120; outputs 60 × 5 = 300; enquiries 20 × 4 = 80; files 5 × 10 = 50; interfaces 4 × 7 = 28. UFP = 120 + 300 + 80 + 50 + 28 = 578. All 14 adjustment values are "average = 3": ΣFᵢ = 42, CAF = 0.65 + 0.42 = 1.07. FP = 578 × 1.07 = 618.46.

Diagrams

  • DFD (data flow diagram): how data moves between processes (functional view).
  • ER diagram: structure of data (static view).
  • UML: object-oriented modelling (class, sequence, use-case diagrams).
  • Structure chart: module hierarchy and calls. HIPO (Hierarchy + Input-Process-Output) charts document a system's functions as a hierarchy.
