20 · Functional Dependencies & Normalization

Module F · DatabasesAsked in 2023 and 2025 Why bad table design causes trouble, and how to read and apply the normal forms.

Start here: the problem normalization solves

Suppose one table stores orders like this:

order_idcustomercustomer_cityitem
1AshaPunePen
2AshaPuneBook
3AshaPuneBag

Asha's city is stored three times. Three kinds of trouble follow: update anomaly (change her city in one row but forget the others: now the data disagrees), insertion anomaly (can't record a customer who hasn't ordered yet), deletion anomaly (deleting her last order loses the fact that she exists). Normalization is the process of splitting tables so each fact is stored once.

Functional dependencies (FDs)

X → Y ("X determines Y") means: whenever two rows agree on X, they must agree on Y. Example: roll_no → name (a roll number determines the name). customer → customer_city.

Closure: the main tool

The closure X⁺ of a set of attributes X is everything X determines (directly or through chains). Algorithm: start with X⁺ = X; keep adding the right side of any FD whose left side is already inside X⁺; stop when nothing new is added.

Worked example: finding a candidate key (2025 question)

R(A, B, C, D, E, P, G) with FDs: AB → CD, DE → P, C → E, P → C, B → G.

  1. Look for attributes that never appear on a right-hand side: A and B. So any key must contain A and B.
  2. Compute (AB)⁺: start {A, B}. AB → CD adds C, D. B → G adds G. C → E adds E. DE → P adds P (now we have D and E). Result: {A, B, C, D, E, G, P}: every attribute.
  3. So AB is a candidate key, and it is the only one (A and B are both required). Prime attributes (part of some key): A, B. Non-prime: C, D, E, P, G.

The normal forms, step by step

FormRuleTypical violation
1NFEvery cell holds a single atomic value; no repeating groupsA "phones" cell containing "111, 222"
2NF1NF, and no partial dependency: no non-prime attribute depends on only part of a candidate keyKey (A,B) but B → G
3NF2NF, and no transitive dependency. Precisely: for every FD X → A, either X is a super key or A is a prime attributecustomer_city depends on customer, which is not a key
BCNFFor every non-trivial FD X → A, X must be a super key (stricter than 3NF)A prime attribute determined by a non-key
4NFBCNF, and no non-trivial multivalued dependencyIndependent multi-valued facts stuffed in one table
5NFNo non-trivial join dependency that isn't implied by the keys

Memory hook: 2NF = "the whole key", 3NF = "nothing but the key", BCNF = "so help me Codd." Each level removes one more kind of redundancy. 5NF is the one concerned with join dependency.

Applying it (continuing the 2025 example)

Key is AB. Check each FD for partial dependency: B → G has a left side (B) that is only part of the key, and G is non-prime. That is a partial dependency, so R is not in 2NF (and therefore not in 3NF or BCNF either).

Fixing: decompose into R1(B, G) and R2(A, B, C, D, E, P) and continue checking.

Quick test order for the exam
  1. Find all candidate keys with closures.
  2. For each FD X → A: if X is a super key, fine.
  3. If not, but A is prime: OK for 3NF, violates BCNF.
  4. If not and A is non-prime: if X is a proper part of a key, it violates 2NF; otherwise (X is not part of any key) it violates 3NF but not 2NF.

Check yourself

ISRO 2025 · Q48

Consider R = (A, B, C, D, E, P, G) and the functional dependencies AB→CD, DE→P, C→E, P→C, B→G. Which one of the following is true?

The only candidate key is AB. The FD B → G is a partial dependency (non-prime G depends on part of the key), so R is not in 2NF.

Fifth Normal form is concerned with

5NF (project-join normal form) deals with join dependencies. Multivalued dependency is 4NF; functional dependencies drive 2NF–BCNF.
