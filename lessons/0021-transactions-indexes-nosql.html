21 · Transactions, Indexes & NoSQL

Module F · DatabasesAsked in 2023 and 2025 ACID, concurrency, isolation levels, indexing, and non-relational databases.

Start here: what is a transaction?

A transaction is a group of database operations that must be treated as one unit. Classic example: transfer ₹1000 from account A to B. It means (1) subtract 1000 from A, (2) add 1000 to B. If the system crashes between the two steps, ₹1000 vanishes. So either both steps happen or neither does.

A transaction ends with commit (make permanent) or rollback/abort (undo everything).

Concurrency problems and isolation levels

Running transactions at the same time is faster but can cause:

  • Dirty read: reading data another transaction wrote but hasn't committed (it may roll back).
  • Non-repeatable read: reading the same row twice and getting different values because another transaction changed it between your reads.
  • Phantom read: running the same query twice and getting extra rows because another transaction inserted some.
  • Lost update: two transactions overwrite each other's changes.

Serializability

A schedule is the interleaving of operations from several transactions. It is serializable if its effect equals that of some serial (one-at-a-time) order. To test conflict serializability: two operations conflict if they touch the same item, belong to different transactions, and at least one is a write. Draw a precedence graph with an edge Ti → Tj when a conflicting operation of Ti comes before one of Tj. No cycle ⇒ conflict-serializable.

Locking

Transactions take shared (S) locks to read and exclusive (X) locks to write. Two-phase locking (2PL): a transaction first only acquires locks (growing phase), then only releases them (shrinking phase); this guarantees serializability. But locking can cause deadlock: T1 holds a lock on A and wants B, while T2 holds B and wants A. The DBMS detects the cycle (wait-for graph) and rolls one transaction back to break it.

Worked scenario: two transfers can deadlock (2025 Q47)

T1 moves ₹1000 from A to B (operations: read A, read B, write A, write B). T2 moves ₹1000 from B to A (read B, read A, write B, write A). Under locking at REPEATABLE READ, each read takes a shared lock. Suppose T1 reads A and T2 reads B, then T1 reads B and T2 reads A (all shared locks are compatible). Now T1 wants to write A, which needs an exclusive lock, but T2 holds a shared lock on A; T2 wants to write B, but T1 holds a shared lock on B. Each waits for the other: deadlock. The DBMS detects it and rolls back one transaction (either may be the victim), after which the other completes. If they run one after the other, both transfers apply and both balances end at ₹5000. If only T1 survives, the result is A = 4000, B = 6000. The question asked which outcome can never occur; work through each option with these cases and check the answer against your key, because I could not settle it from the text alone.

Recovery

Changes are written to a log first (write-ahead logging) so after a crash the DBMS can redo committed work and undo uncommitted work. Checkpoints limit how much log must be replayed.

Indexes

An index is like the index of a book: a separate structure that lets the DBMS find rows without scanning the whole table. Most are B+ trees: balanced trees with O(log n) search whose leaves are linked in sorted order, good for both equality and range queries. A clustered index determines the physical order of rows (one per table); non-clustered indexes are separate (many allowed). Indexes speed up reads but slow down inserts/updates and use space.

Composite index rule (leftmost prefix). An index on (country, city, street) is sorted by country, then city within country, then street within city. It helps queries that give country, or country and city, or all three. It does not help a query that gives only street (or only city): the streets are scattered across the whole index, like looking up a street in a phone book sorted by country and city.

NoSQL databases

"NoSQL" ("not only SQL") databases drop some relational rules to scale across many machines and handle varied data. Typical characteristics: flexible (schema-less) structure, horizontal scaling, often looser consistency (BASE: basically available, soft state, eventually consistent), and queries that often don't use SQL.

ISRO 2023 · Q33

Amongst the ACID properties of a transaction, the 'Durability' property requires that the changes made to the database by a successful transaction persist

Durability is the strongest promise: committed work must survive any failure (practically, via logs and backups).

A table users(userid, country, city, street) has 50 million users. A DBA creates the index myindex ON users(country, city, street). For which query will this index be least useful?

Leftmost-prefix rule: a query on street alone skips the leading columns.
