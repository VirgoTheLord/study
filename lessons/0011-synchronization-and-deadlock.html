11 · Synchronization & Deadlock

Module C · Operating systemsAsked in 2023 and 2025 Race conditions, semaphores, producer–consumer, priority inversion, deadlock and Banker's algorithm.

Start here: why do processes need to coordinate?

Several processes or threads often share data. If they touch it at the same moment, the result can be garbage. Imagine two people editing the same bank balance at once: both read ₹100, one adds 50 and the other subtracts 30; whoever writes last overwrites the other's work.

A race condition is a situation where several processes access and manipulate the same data concurrently and the outcome depends on the particular order in which the accesses happen.

Worked example: why counter++ is not safe

counter++ is really three machine steps: (1) load counter into a register, (2) add 1, (3) store it back. Let counter = 5 and let two threads each run it once. If thread A loads 5, then thread B loads 5, both add 1 to get 6, and both store 6, the final value is 6, not 7. One increment was lost.

The critical-section problem

The part of code that touches shared data is the critical section. A correct solution must provide: mutual exclusion (only one process inside at a time), progress (if nobody is inside, someone waiting can enter without unreasonable delay) and bounded waiting (no process waits forever).

Tools for synchronisation

ToolWhat it is
Mutex lockA lock with two states. You acquire it before the critical section and release it after. Only the owner releases it.
SpinlockA lock where a waiting thread loops ("spins") checking the lock. Wastes CPU but avoids a context switch; fine for very short waits.
SemaphoreAn integer variable changed only through two atomic operations: wait(S) (also P): if S > 0 decrement it, otherwise block; and signal(S) (also V): increment S and wake a waiter. A binary semaphore (0/1) acts like a mutex; a counting semaphore counts available units of a resource.
MonitorA language-level construct: a bundle of data and procedures where only one process can be active at a time, with condition variables to wait for events.

Classic problem: producer–consumer (bounded buffer)

A producer puts items into a buffer of size N; a consumer takes them out. The producer must wait when the buffer is full; the consumer must wait when it is empty. Three semaphores solve it:

mutex = 1      // protects the buffer itself
empty = N      // number of empty slots
full  = 0      // number of filled slots

Producer:            Consumer:
  wait(empty)          wait(full)      // blocks if buffer is empty
  wait(mutex)          wait(mutex)
  put item             take item
  signal(mutex)        signal(mutex)
  signal(full)         signal(empty)

The consumer waits on full when the buffer is empty: this is a case of "wait until a condition becomes true", for which a semaphore is the right primitive (a plain mutex only gives exclusion, it doesn't count items).

Other classics: readers–writers (many readers may read together, but a writer needs exclusive access) and dining philosophers (five philosophers share five forks; if all pick up the left fork at once, nobody can eat: a deadlock).

Priority inversion

A low-priority task L holds a lock. A high-priority task H needs that lock and must wait. Meanwhile a medium-priority task M (which doesn't need the lock) preempts L. Now H, the most important task, is effectively waiting behind M. This is priority inversion. The priority inheritance protocol fixes it: while L holds the lock that H wants, L temporarily inherits H's priority, so M can't preempt it, L finishes quickly and releases the lock.

Deadlock

A set of processes is deadlocked when each is waiting for a resource that another process in the set holds, so none can ever proceed.

Example: process A holds lock 1 and wants lock 2; process B holds lock 2 and wants lock 1. Both wait forever.

Four necessary conditions (all must hold at once):
1. Mutual exclusion: a resource can be used by only one process at a time.
2. Hold and wait: a process holds some resources while waiting for others.
3. No preemption: resources cannot be forcibly taken away.
4. Circular wait: a cycle of processes, each waiting for the next one's resource.
Break any one and deadlock is impossible.

Resource-allocation graph and wait-for graph

In a resource-allocation graph, processes are circles and resources are squares. An arrow from a resource to a process means "held by"; from a process to a resource means "requests". A cycle means deadlock if each resource has a single instance. The wait-for graph is a simplified version: remove the resource nodes and draw an arrow Pi → Pj when Pi is waiting for a resource held by Pj. A cycle in the wait-for graph = deadlock.

Handling deadlock

  • Prevention: ensure at least one of the four conditions can never hold (e.g. force a global lock order to avoid circular wait).
  • Avoidance: grant a request only if the system stays in a safe state (Banker's algorithm).
  • Detection and recovery: let it happen, find it with a graph algorithm, then abort a process or preempt resources.

Banker's algorithm and safe states

A state is safe if there exists some order in which all processes can run to completion (a safe sequence). Terms: Allocation (held now), Max (the most it will ever need), Need = Max − Allocation, Available (free now).

  1. Set Work = Available.
  2. Find a process not yet finished whose Need ≤ Work.
  3. Pretend it runs to completion and returns its resources: Work = Work + its Allocation.
  4. Repeat. If every process finishes, the state is safe; if you get stuck, it is unsafe.
Worked example (2025 question)

Resources A=10, B=5, C=7. Allocation: P0 (0,1,0), P1 (2,0,0), P2 (3,0,2). Max: P0 (7,5,3), P1 (3,2,2), P2 (9,0,2). Available (5,4,5).

  1. Need: P0 = (7,4,3), P1 = (1,2,2), P2 = (6,0,0).
  2. Work = (5,4,5). P0's need (7,…) is too big. P1's need (1,2,2) fits. Run P1: Work = (5,4,5) + (2,0,0) = (7,4,5).
  3. P2 needs (6,0,0) ≤ (7,4,5). Run P2: Work = (7,4,5) + (3,0,2) = (10,4,7).
  4. P0 needs (7,4,3) ≤ (10,4,7). Run P0: Work = (10,5,7).

All finished. Safe sequence: P1, P2, P0. The system is in a safe state.

ISRO 2023 · Q53

In a producer-consumer scenario (bounded-buffer problem), what would be the most appropriate synchronization primitive to ensure that the consumer waits when the buffer is empty?

A counting semaphore (full) makes the consumer block until an item exists. (A monitor with a condition variable could do it too, but among these, the semaphore is the standard answer.)

A resource-allocation graph shows: P1 holds R1 and requests R2; P2 holds R2 and requests R1; each resource has one instance. The corresponding wait-for graph is

P1 waits for R2, held by P2: edge P1 → P2. P2 waits for R1, held by P1: edge P2 → P1. A cycle means deadlock.
